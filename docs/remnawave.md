# Remnawave → MultiCore

Инструкция для тех, у кого подписки раздаёт [Remnawave](https://docs.rw). Нужны **MultiCore 1.0.1+** и Remnawave с Response Rules (v2.2+). Проверено на исходниках Remnawave backend v3.4.

**Коротко:** один шаблон Mihomo, два Response Rules и, по желанию, кнопка на странице подписки. Ремну патчить не нужно.

## Как это работает и почему именно так

MultiCore запрашивает подписку тремя User-Agent (подробнее — в [документации для провайдеров](providers.md)). Что с ними делает Ремна:

| Запрос MultiCore | Что умеет Ремна | Итог |
|---|---|---|
| `multicore-mihomo` | Тип ответа `MIHOMO` по вашему шаблону | ✅ Основной конфиг |
| `multicore-xray` | `XRAY_JSON` у Ремны — **массив** конфигов (по одному на хост), а MultiCore нужен **один** объект с мостами | ❌ Не подходит |
| `multicore-json-massive` | Такого формата у Ремны нет | ❌ Не подходит |

Все серверы Ремны (VLESS/Reality, Trojan, Shadowsocks, Hysteria2 и т. д.) Mihomo подключает сам. Поэтому с версии 1.0.1 MultiCore понимает подписку «только Mihomo»: если в конфиге нет мостов в Xray, ответ Xray не нужен, и клиент запускает пустой Xray. Ремне достаточно правильно отдавать Mihomo.

## Шаг 1. Шаблон Mihomo «MultiCore»

В панели откройте **Templates → Mihomo**, создайте шаблон с именем `MultiCore` и вставьте [multicore-mihomo-template.yaml](remnawave/multicore-mihomo-template.yaml).

Чем он отличается от стандартного шаблона Ремны и почему:

- **`tun` включён,** потому что MultiCore подключается через TUN. Стандартный шаблон Ремны рассчитан на прокси-режим (`mixed-port`, `allow-lan: true`).
- **`allow-lan: false`, без `mixed-port` и `external-controller`.** Порт управления и секрет клиент ставит сам, а открывать прокси в локальную сеть незачем.
- **DNS в режиме fake-ip, `proxy-server-nameserver` на DoH.** Адреса ваших серверов резолвятся напрямую и не зависят от самого туннеля.
- **Группа `url-test` «⚡ Автовыбор».** MultiCore показывает её как «Автовыбор → 🇸🇪 Sweden», с реальным узлом.
- **`find-process-mode: always`.** Можно писать правила по процессам (`PROCESS-NAME`).

Метки `# LEAVE THIS LINE!` не трогайте: на их место Ремна вставит серверы. Правила (`rules`) меняйте как хотите, это и есть ваша маршрутизация.

## Шаг 2. Response Rules

Откройте редактор **Response Rules** и добавьте в **самый верх** списка два правила из [response-rules.json](remnawave/response-rules.json):

```json
{
  "name": "MultiCore",
  "enabled": true,
  "operator": "AND",
  "conditions": [
    { "headerName": "user-agent", "operator": "EQUALS", "value": "multicore-mihomo", "caseSensitive": true }
  ],
  "responseType": "MIHOMO",
  "responseModifications": { "subscriptionTemplate": "MultiCore" }
},
{
  "name": "MultiCore: без Xray",
  "enabled": true,
  "operator": "OR",
  "conditions": [
    { "headerName": "user-agent", "operator": "EQUALS", "value": "multicore-xray", "caseSensitive": true },
    { "headerName": "user-agent", "operator": "EQUALS", "value": "multicore-json-massive", "caseSensitive": true }
  ],
  "responseType": "STATUS_CODE_404"
}
```

Почему так:

- **Правила должны стоять выше стандартных.** Ремна проверяет их сверху вниз, и срабатывает первое подходящее. Иначе MultiCore попадёт в последнее стандартное правило и получит base64.
- **Первое правило.** Отдаёт Mihomo именно по шаблону `MultiCore`, а не по «Default». Тогда остальные клиенты (FlClash, Clash Verge и т. п.) продолжают получать свой обычный шаблон.
- **Второе правило необязательно.** Без него MultiCore получит на эти запросы base64 и тоже справится. С ним ответ быстрее и в диагностике чище.

## Шаг 3. Заголовки (по желанию)

**Subscription → Settings → Response Headers.** Ниже — самые нужные. Полный список заголовков, которые понимает MULTICORE (анонсы с кнопкой и цветом, `dumb-mode`, `app-language`, логотип и другие), — в [описании для провайдеров](providers.md#заголовки-ответа-которые-понимает-клиент). В Ремне любой из них задаётся здесь же; кириллицу и эмодзи передавайте через `rwEncodeBase64:`.

| Заголовок | Пример значения | Что увидит пользователь |
|---|---|---|
| `profile-title` | `rwEncodeBase64:Мой VPN` | Название подписки. `rwEncodeBase64:` обязателен для кириллицы и эмодзи |
| `profile-update-interval` | `6` | Как часто (в часах) приложение само обновляет подписку |
| `support-url` | `https://t.me/myvpn_support` | Кнопка «Поддержка» |
| `profile-web-page-url` | `{{SUBSCRIPTION_URL}}` | Кнопка «Личный кабинет» |
| `announce` | `rwEncodeBase64:Плановые работы 20:00–21:00` | Анонс. Всплывает сам только при изменении текста |
| `myvpn-servicelogo` | `https://cdn.example.com/logo.png` | Логотип в заголовке окна. Префикс любой, но не пустой. SVG будет чётче всего |
| `myvpn-app-language` | `en` | Язык интерфейса (`ru`/`en`), если пользователь не выбрал свой |
| `myvpn-dumb-mode` | `on` | Показывать только первую группу, без вкладок |

Трафик и срок (`subscription-userinfo`) Ремна отправляет сама.

## Шаг 4. Лимит устройств (HWID)

MultiCore всегда отправляет `x-hwid`, `x-device-os`, `x-ver-os` и `x-device-model`, так что лимит устройств Ремны работает из коробки.

- **Какой ID.** Стабильный, привязан к установке Windows или Linux. Переустановка приложения его не меняет.
- **Что видно в панели.** ОС, её версия и модель устройства, например `windows` · `Windows 11 Pro 24H2`.
- **Когда лимит исчерпан,** пользователь увидит «Достигнут лимит устройств для этой подписки» вместо непонятной ошибки.

## Шаг 5. Кнопка на странице подписки

В **Subpage Builder** добавьте приложение в платформу `windows` (и `linux`, если нужно). Готовый блок — [subpage-app.json](remnawave/subpage-app.json). Главное в нём — кнопка:

```json
{ "link": "multicore://add/{{SUBSCRIPTION_LINK}}", "type": "subscriptionLink",
  "text": { "ru": "Добавить в MultiCore", "en": "Add to MultiCore" }, "svgIconKey": "Plus" }
```

- **Иконки и цвета.** `svgIconKey` и `svgIconColor` замените на ключи и цвета, которые есть в `svgLibrary` вашего конфига.
- **Ссылка на установщик.** `…/releases/latest/download/MultiCore-Setup-x64.exe` всегда указывает на свежую версию.
- **Linux.** Лучше ссылайтесь на [страницу релизов](https://github.com/fatyzzz/multicore-releases/releases/latest): в именах пакетов есть номер версии.

## Проверка

```sh
curl -s -A multicore-mihomo -H "x-hwid: TEST-DEVICE-0001" \
  https://sub.example.com/api/sub/<shortUuid> | head -40
```

- **Что должно прийти:** YAML с `tun:`, вашими серверами в `proxies:` и группами.
- **Если пришёл base64:** правило стоит ниже стандартных или выключено.
- **Если пришёл пустой ответ:** смотрите заголовки (`curl -D -`). `x-hwid-max-devices-reached: true` означает, что лимит устройств исчерпан. Тестовый HWID потом удалите у пользователя в панели.

## А если нужен настоящий «мульти-кор» с Xray?

Режим «только Mihomo» закрывает всё, что умеет Mihomo. Xray нужен, если хотите транспорты, которых в Mihomo нет: свежие режимы XHTTP, FinalMask и прочую маскировку, которая сначала появляется в Xray. Тогда MultiCore нужен **один** объект Xray с мостами, связанный с Mihomo по именам и портам. Стоковая Ремна так не умеет. Три пути:

### 1. Свой сервер подписок — рекомендуем для серьёзных сетапов

Небольшой сервис отдаёт по ссылке три ответа по [контракту](providers.md): Mihomo с мостами `socks5 127.0.0.1:310xx`, Xray с такими же inbound и связку обоих. Данные о пользователях, трафике и сроках он берёт из API Ремны. Ремна остаётся панелью управления, а подписку для MultiCore собираете вы.

- **Плюсы:** полный контроль, любые транспорты, обновления Ремны ничего не ломают.
- **Минусы:** это ваш код, и его нужно поддерживать.

### 2. Адаптер перед Ремной — в планах

Прослойка между пользователем и `/api/sub/…`. Для запросов MultiCore она:
1. берёт у Ремны Mihomo и массив `XRAY_JSON`;
2. хосты с тегом, например `MULTICORE_XRAY`, превращает в пары «SOCKS-мост в Mihomo ↔ inbound и outbound в Xray»;
3. отдаёт готовый комплект по контракту.

Все остальные клиенты проходят сквозь неё без изменений. Ремну патчить не нужно: адаптер работает как обычный reverse proxy перед ней. Точный алгоритм — в [llms-full.txt](../llms-full.txt), раздел 7: его можно отдать разработчику или ИИ как ТЗ.

### 3. Форк Ремны с «родным» форматом — не советуем

Технически можно добавить в backend Ремны тип ответа `MULTICORE`. Но Ремна обновляется очень часто, и каждое обновление придётся заново сливать с форком: конфликты в модулях подписок, пересборка образа, риск сломать выдачу всем клиентам разом. Через пару месяцев вы будете разбираться в чужом коде вместо своего VPN.

Правильная версия этого пути — нативная поддержка в самой Ремне, через PR в upstream. Мы готовы с этим помогать. Когда (и если) поддержку примут, пункты 1 и 2 станут не нужны.
