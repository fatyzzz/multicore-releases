# Как устроен MultiCore

## Почему два ядра

У **Mihomo** (бывший Clash Meta) лучший движок маршрутизации: TUN, DNS с fake-ip, правила по доменам, IP и процессам, группы с автовыбором по пингу. **Xray** раньше всех получает новые транспорты и способы маскировки, и некоторых из них в Mihomo нет вовсе.

MultiCore запускает оба ядра и связывает их:

```
приложения ─► TUN (Mihomo: DNS, правила, группы)
                 │
                 ├─► VLESS / Reality / Hysteria2 / … — Mihomo подключается сам
                 │
                 └─► socks5 127.0.0.1:310xx ─► Xray ─► транспорт, которого нет в Mihomo
```

- **Все серверы умеет Mihomo.** Если провайдер отдаёт только его конфиг, Xray стоит пустым и трафик не трогает. Это режим «только Mihomo»: так работают, например, подписки из Remnawave.
- **Нужен Xray.** Тогда провайдер кладёт в конфиг Mihomo локальные SOCKS-мосты `127.0.0.1:<порт>`. Каждый мост в конфиге Xray ведёт в свой outbound.
- **Кто за что отвечает.** Группы, выбор сервера и пинг всегда живут в Mihomo. Xray только «несёт» трафик до сервера.

## Служба MultiCore (с версии 1.1.0)

При установке «Со службой» привилегированная часть — служба `MultiCore` (Windows) или `multicore.service` (systemd) — ставится один раз:

1. Когда вы открываете приложение, служба запускает Mihomo и Xray с выключенным TUN. Пинги, группы и «Автовыбор → узел» работают сразу.
2. «Подключить» только включает TUN у уже работающего Mihomo (или системный прокси в режиме без TUN). Это доли секунды и без UAC/pkexec.
3. «Отключить» выключает TUN, ядра остаются готовыми. «Выход» из трея останавливает ядра, служба засыпает.
4. Служба запускает только ядра из защищённой папки установки, конфиг подписки копирует к себе и пропускает через строгую очистку: никаких путей к файлам, лишних портов и опасных функций. Управление Mihomo идёт только через фильтрованный контроллер, поэтому ни приложение, ни дашборд не могут, например, подменить ядро или переписать конфиг.

Без службы всё работает как описано ниже.

## Что происходит при подключении (без службы)

1. Программа и её фоновая служба работают от вашего пользователя.
2. По кнопке «Подключить» запускается отдельный процесс `multicore-core-host` с правами администратора. На Windows это запрос UAC, на Linux — `pkexec`. Права нужны только ему: он создаёт TUN-адаптер и запускает ядра.
3. Сначала стартует Xray, затем Mihomo. Приложение ждёт, пока оба реально готовы: порты открыты, первое соединение прошло.
4. При отключении сначала останавливается Mihomo, потом Xray. Если приложение упало, ядра умирают вместе с процессом-хостом (Job Object на Windows, группа процессов на Linux).

Приложение вмешивается в конфиг провайдера минимально:
- ставит свой адрес и секрет панели управления Mihomo;
- даёт TUN-адаптеру имя `MultiCore`;
- добавляет Xray прямой DNS для адресов серверов, чтобы подключение не зависело от самого себя.

Всё остальное — правила, DNS, группы — работает ровно так, как написал провайдер.

## Режим без TUN (Windows)

Настройки → выключить TUN.

- **Как работает.** Mihomo слушает локальный порт на `127.0.0.1`, а Windows получает его как системный прокси. Прав администратора не нужно, UAC не появится.
- **Цена.** Через VPN идут только программы, которые уважают системный прокси: браузеры и большинство приложений. Игры, торренты и консольные утилиты обычно пойдут напрямую.
- **Безопасность настроек.** При отключении, сбое или следующем запуске после падения прежние настройки прокси возвращаются как были.

## Подписка

- **Какие данные забираются.** По ссылке подписки приложение запрашивает конфиги с «говорящим» User-Agent: `multicore-json-massive`, `multicore-mihomo`, `multicore-xray`. По нему сервер понимает, что отдать. Подробно — в [документации для провайдеров](providers.md).
- **Когда обновляется.** При запуске приложения и по интервалу `profile-update-interval` (по умолчанию каждые 6 часов). Если обновление не удалось, остаётся последняя рабочая версия. Новая версия конфига применяется при следующем подключении и не рвёт текущее.
- **Сетевые детали.** Запросы идут напрямую, а при недоступности — один повтор через системный прокси. HTTPS нельзя «понизить» до HTTP редиректом. Публичный адрес не может перенаправить на локальную сеть.

## Почему сборки не подписаны

Сертификат для подписи кода стоит денег и времени, проект пока без него. Поэтому:
- SmartScreen предупреждает при первом запуске;
- целостность обеспечивается суммами SHA-256 в каждом релизе, а автообновление проверяет каждый файл.

Программа ставится в профиль пользователя, и файлы, которые запускаются с правами администратора, лежат в папке, доступной пользователю на запись. Это осознанный компромисс превью-версий: установка без прав администратора ценой более слабой изоляции.

## Где что лежит

| | Windows | Linux |
|---|---|---|
| Программа | `%LOCALAPPDATA%\Programs\MultiCore\current` | `/usr/lib/multicore` |
| Данные (подписки, настройки) | `%LOCALAPPDATA%\MultiCore` | `~/.local/share/multicore` |
| Автозапуск | реестр HKCU `Run` | `~/.config/autostart/multicore.desktop` |

Удаление программы не стирает данные. Чтобы убрать и подписки, удалите папку данных после выхода из приложения.
