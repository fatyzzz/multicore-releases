# Провайдерам: подписка для MultiCore

MultiCore принимает не общие подписки (списки `vless://…`, base64, sing-box), а **готовые конфиги ядер**. Правила, DNS и группы полностью в ваших руках, клиент их не переписывает.

> Используете **Remnawave**? Вам сразу сюда: [Remnawave → MultiCore](remnawave.md).

## Что клиент запрашивает

Клиент ходит по одной и той же ссылке подписки и выбирает формат через `User-Agent`:

| User-Agent | Что вернуть |
|---|---|
| `multicore-json-massive` | JSON-массив из двух элементов: `["<Mihomo YAML строкой>", {<объект Xray>}]` |
| `multicore-mihomo` | Полный Mihomo YAML, готовый к запуску |
| `multicore-xray` | **Один** объект Xray JSON (не массив) |

Порядок запросов:

1. **Сначала `multicore-json-massive`.** Если пришёл `2xx` и тело начинается с `[`, это окончательный ответ. Даже если он невалидный, запасных запросов не будет.
2. **Иначе — два параллельных запроса.** На любой другой ответ (HTML, base64, 404, сетевая ошибка) клиент параллельно шлёт `multicore-mihomo` и `multicore-xray`.
3. **Нужны оба ответа.** Mihomo и Xray должны прийти и быть валидными. Исключение — режим «только Mihomo», он описан ниже.

### Режим «только Mihomo» (с версии 1.0.1)

Если в Mihomo YAML **нет** локальных мостов в Xray (`socks5` на `127.0.0.1`), то Xray не нужен:
- **Ответ на `multicore-xray` необязателен.** Это может быть 404, base64 или массив. Клиент запустит пустой Xray.
- **Если вернули валидный объект Xray,** клиент его всё равно использует.

Так проще всего поддержать MultiCore из любой панели, которая умеет отдавать Mihomo.

### Режим «Mihomo + Xray» (мосты)

Этот режим нужен, когда часть серверов работает на транспортах, которых нет в Mihomo:

**В Mihomo** — по одному SOCKS-прокси на каждый такой сервер:

```yaml
proxies:
  - name: "🇳🇱 Netherlands"
    type: socks5
    server: 127.0.0.1
    port: 31001
    udp: true
```

**В Xray** — inbound с тем же `tag` и портом плюс правило, которое ведёт его в нужный outbound:

```json
{
  "inbounds": [
    { "tag": "🇳🇱 Netherlands", "listen": "127.0.0.1", "port": 31001, "protocol": "socks",
      "settings": { "auth": "noauth", "udp": true, "ip": "127.0.0.1" } }
  ],
  "outbounds": [ { "tag": "nl-1", "protocol": "…", "settings": {}, "streamSettings": {} } ],
  "routing": { "rules": [ { "type": "field", "inboundTag": ["🇳🇱 Netherlands"], "outboundTag": "nl-1" } ] }
}
```

Требования:
- **Мосты** слушают только `127.0.0.1`, порты уникальны.
- **Одна ревизия.** Обе половины должны быть собраны из одного состояния.
- **Чего не должно быть в Xray:** TUN, своя DNS-политика, маршрутизация по процессам — этим владеет Mihomo.
- **Порядок запуска.** Клиент стартует Xray первым, Mihomo вторым.

### Что должно быть в Mihomo YAML

- **Обязательные блоки:** `tun` (enable, auto-route, auto-detect-interface, `dns-hijack`), `dns`, `rules`, `proxy-groups`.
- **Необязательные:** `sniffer`, `rule-providers`, правила `PROCESS-NAME`.
- **Что клиент перепишет сам:** `external-controller`, `secret`, `external-ui` и имя TUN-устройства. В режиме без TUN он также выключает `tun` и ставит свой `mixed-port` на `127.0.0.1`.
- **`url-test`-группы** показываются в приложении как «Автовыбор → реальный узел».
- **Значки групп:** поле `icon:` у группы в `proxy-groups` — HTTPS-ссылка на PNG/JPEG/WebP/SVG. Клиент скачивает значки при обновлении подписки (до 32 штук, без редиректов, до 512 KiB) и показывает их во вкладках групп и в трее; без значка остаётся эмодзи из названия.

Готовый пример — [шаблон для Remnawave](remnawave/multicore-mihomo-template.yaml). Он подходит и без Remnawave: на место меток `# LEAVE THIS LINE!` вставьте свои серверы.

## Заголовки запроса

Каждый запрос конфига несёт:

| Заголовок | Значение |
|---|---|
| `x-hwid` | Стабильный ID установки, UUID в верхнем регистре. Совместим со схемой INCY |
| `x-device-os` | `windows` или `linux` |
| `x-ver-os` | Версия ОС |
| `x-device-model` | Модель устройства, по умолчанию `Windows PC` / `Linux PC` |

Запрос логотипа (`User-Agent: multicore-service-logo`) эти заголовки **не** отправляет.

## Заголовки ответа, которые понимает клиент

| Заголовок | Что делает |
|---|---|
| `profile-title` | Название подписки. Можно `base64:<…>` для не-ASCII, до 128 символов. Запасные варианты: `<vendor>-servicename`, затем `filename` из `Content-Disposition` |
| `subscription-userinfo` | `upload=…; download=…; total=…; expire=…`. Байты и unix-время; `0` означает «без лимита» |
| `profile-update-interval` | Интервал автообновления в часах, от 15 минут до 30 дней. По умолчанию 6 часов |
| `profile-web-page-url` | Кнопка «Личный кабинет» (`http`/`https`) |
| `support-url` | Кнопка «Поддержка» (`http`/`https`/`tg`) |
| `<vendor>-servicelogo` | Логотип сервиса: HTTPS-ссылка на PNG/JPEG/WebP/SVG, например `myvpn-servicelogo`. Нужен непустой префикс |
| `announce` | Анонс в приложении, до 512 символов, можно `base64:`. Всплывает сам, только когда текст изменился. `0` скрывает анонс |
| `announce-url` | Ссылка из анонса |
| `sub-info-button-text` | Подпись кнопки в анонсе, до 32 символов |
| `sub-info-color` | Цвет анонса: `blue`, `green` или `red` |
| `dumb-mode` | `on` — показывать в приложении только первую группу из `proxy-groups`, без вкладок групп (на главной и в трее). Остальные группы продолжают работать. Можно с префиксом: `myvpn-dumb-mode`. Значения `on`/`off`, `true`/`false`, `1`/`0`; по умолчанию `off` |
| `X-Hwid-Max-Devices-Reached: true` | Приложение покажет «Достигнут лимит устройств» вместо непонятной ошибки |

Совместимые синонимы: `sub-info-text` / `banner-text` для `announce`, `sub-info-button-link` / `banner-button-url` для `announce-url`.

**Намеренно не поддерживаются** удалённые настройки интерфейса: `*-background`, виджеты, `routing`, `hide-settings`. Правила и так целиком приходят в конфиге.

## Кнопка «Добавить в MultiCore»

```
multicore://add/https://sub.example.com/api/sub/AbC123
```

- **Ссылка вставляется как есть,** в том же стиле, что `happ://add/…`.
- **Строгий вариант** тоже работает: `multicore://install-sub?url=<ссылка в percent-encoding>`.
- **Подтверждение.** Приложение покажет хост подписки и спросит, добавлять ли её.
- **Где работает.** Схема регистрируется установщиком на Windows и пакетами deb/rpm/Arch на Linux. Портативная версия и AppImage её не регистрируют.

## Ошибки, которые увидит пользователь

Клиент различает причины и пишет их по-человечески:
- сервер недоступен, таймаут, ошибка TLS;
- 401/403, 404/410, 429, 5xx;
- «пришла веб-страница или список ссылок, а не подписка MultiCore»;
- повреждённый конфиг;
- лимит устройств.

Ссылка подписки никогда не попадает ни в текст ошибок, ни в диагностику.
